## Commands

The package manager is pnpm (pinned via `packageManager` in `package.json`).

- `pnpm dev`: dev server at http://localhost:3000 (`pnpm dev -H 0.0.0.0` to expose it on the network)
- `pnpm build` / `pnpm start`: production build and server. With `DATABASE_URL` set (`.env.local`) the build prerenders docs pages from the database; without it, it builds with empty public data (see Image builds).
- `pnpm lint`: ESLint (flat config in `eslint.config.mjs`, using `eslint-config-next` core-web-vitals + typescript)
- Type-check: `pnpm exec tsc --noEmit`
- Database: `pnpm db:up` (docker compose, Postgres on 127.0.0.1:5491), `pnpm db:generate` (migration from `db/schema.ts` into `db/migrations/`), `pnpm db:migrate`, `pnpm db:seed [--force]`, `pnpm db:studio`

- Production: `pnpm prod:deploy` (`deploy/deploy.sh`) starts Postgres, pulls the app image `ghcr.io/teknik-github/docsku:${DOCSKU_VERSION:-latest}`, and starts `app` on `127.0.0.1:${APP_PORT:-3020}` (`docker-compose.prod.yml` layered on `docker-compose.yml`, settings in `.env.production`); `deploy.sh --build` builds the `runner` image locally instead. There is no bundled reverse proxy; the owner's own proxy terminates HTTPS, hence `TRUST_PROXY=1` (or `cloudflare`). `.dockerignore` excludes `.env*`, since `next build` would read them into the image. The container runs as uid 10001 (no host account) with `storage/uploads` bind-mounted, and ships `db/migrations`. `GET /api/health` checks the DB.
- Image builds: `.github/workflows/docker.yml` runs on `v*.*.*` tags (and manual dispatch) and pushes `ghcr.io/<owner>/docsku` (`X.Y.Z` + `latest`, or the branch name, plus `sha-…`). The build has **no database**: `buildingWithoutDatabase` (`db/index.ts`, no `DATABASE_URL` during `next build`) makes the public reads in `lib/data/site.ts` return empty results, and the running server refreshes every page at startup (see Rendering). Each build gets `NEXT_DEPLOYMENT_ID` (version skew protection: old tabs hard-reload instead of failing).
- Migrations run inside the app: `instrumentation.ts` awaits `migrateDatabase()` (`lib/migrate.ts`: drizzle-orm migrator on `db/migrations`, its own connection with an advisory lock, same `drizzle.__drizzle_migrations` table as drizzle-kit) before the server serves requests, and `/admin/setup` calls it again and shows a DB error if it fails. `DISABLE_AUTO_MIGRATE=1` turns it off. New migrations still come from `pnpm db:generate`.

- Releases: `pnpm release X.Y.Z` (`deploy/release.sh`) needs a clean `main` equal to `origin/main` and `gh`. It bumps `package.json`, commits "Release vX.Y.Z", tags, pushes, and creates a GitHub release whose notes are the commit subjects since the previous tag. The tag triggers the image build. The repository and its image are public.

Env: `.env` holds `POSTGRES_PASSWORD` for docker compose. `.env.local` holds `DATABASE_URL`, `CRON_SECRET`, `UPLOAD_DIR`, and `ENCRYPTION_KEY` (optionally `AI_API_KEY`, `SITE_URL`, `TRUST_PROXY`, `SCHEDULER_URL`, `DISABLE_AUTO_MIGRATE`). See `.env.example`.

There is no test framework. Changes have been verified with ad-hoc Playwright scripts.

## Stack and architecture

This is a documentation site styled after platform.claude.com/docs, with a Ghost-like dashboard at `/admin`. It runs on **Next.js 16.4 / React 19.3** (App Router), with PostgreSQL through Drizzle ORM (`db/`) and a TipTap v3 block editor. There is no `src/` directory, and `@/*` maps to the repo root. UI text and sample content are in Indonesian.

### Content model

- Page bodies are **TipTap/ProseMirror JSON** (`jsonb`), not Markdown. Custom block nodes are `callout`, `cardGroup`/`card`, `steps`/`step`, `tabs`/`tab`, `codeGroup`, and `accordion`, and `codeBlock` carries extra `title`/`highlight`/`lineNumbers` attributes. A new block type has to be added in three places: the editor node (`components/admin/editor/nodes.tsx`), the public renderer (`lib/content/render.tsx`), and the Markdown export (`lib/content/markdown.ts`).
- Each `pages` row holds two copies. The **live** columns (`title`/`description`/`content`) are what visitors see. The **working copy** (`draftTitle`/`draftDescription`/`draftContent`) is what the editor autosaves. Publishing copies working → live, and `hasChanges` flags unpublished edits. Statuses are `draft`, `scheduled`, and `published`.
- Navigation and site settings are JSON in the `settings` table (keys `navigation` and `site`; types in `lib/site-types.ts`). Navigation refers to pages by id. `lib/data/site.ts` resolves it into tabs that contain only published pages, so a page must be published **and** listed in navigation to appear in the sidebar and search.
- The home page (`/`) is built at `/admin/home` (`components/admin/home-builder.tsx`, full height via `FULL_BLEED` in the shell): an ordered list of **sections** (`HomeSection` in `lib/site-types.ts`; catalogue, `newSection` and `defaultSections` in `lib/home-sections.ts`; zod in `lib/home-schema.ts`, which also drops stored sections that no longer validate). Types: hero, categories (cards from the navigation sections, with their `image`), articles (popular/latest/featured/manual, list or cards), features, textImage, faq, stats, cta, content (Markdown/MDX through `mdxToDoc` + `RenderDoc`, so `<Tip>`, `<Steps>`… work). Every section has `hidden`, `width` (two consecutive `half` sections share a row) and `tone`. Rendering: `components/home/sections.tsx` (`HomeSections`; every section carries `data-home-section`). Editing autosaves settings key `home_draft` (`saveHomeDraft`, any signed-in user); "Terbitkan" (`publishHome`) copies it to `home` and `updateTag("settings")`; the cached reader is `getHomeSections()`. The builder's preview is an iframe of `/preview/beranda` (signed-in only; the one route whose headers allow framing, by `'self'`, in `next.config.ts`), and `components/home/preview-bridge.tsx` turns clicks there into section selection via `postMessage` (same origin only) and blocks navigation. Until the builder is first published, a published legacy block home (`pages` row with `kind = 'home'`, slug `_home`, edited in the page editor from `lib/content/home-template.ts`) still wins; otherwise `defaultSections()` (the help-centre layout, with fixed `default-*` ids because `/` prerenders it and `Date.now()`/`Math.random()` aren't allowed there) is shown. `getPopularPages` (30-day `page_views`, `cacheLife("hours")`) feeds "popular". Docs queries filter `kind = 'doc'`. The `hero` block (legacy home editor only) renders through `components/blocks/hero.tsx`, and `.prose-home` styles `##` headings as home sections.
- `db/seed/run.mts` converts the sample MDX in `db/seed/docs/` into TipTap JSON (`db/seed/mdx-to-doc.ts`). Those files are seed data only and are not read at runtime.

### Categories (Halaman)

`/admin/pages` is a help-centre style list: categories on the left, the selected category's pages on the right (the shell gives this route, `/admin/comments`, `/admin/review` and `/admin/activity` a full-width layout via `WIDE` in `components/admin/shell.tsx`). A **category is a navigation section and its group is the tab** (`lib/categories.ts`), so the dashboard, the help-centre home and the sidebar share one structure; there is no separate table. A page's category is the section listing it, or its `navSection` while it waits for its first publish ("masuk kategori saat terbit"). "Halaman baru di sini" posts `category` to `createPage`, which lists the new draft in that section at once (drafts stay off the public site; automation won't move a placed page). Admin-only actions in `app/admin/_actions/categories.ts`: create (existing or new group), rename, delete (only when empty and no draft is waiting for it; an emptied group goes too), `movePagesToCategory` (bulk "Pindahkan ke…"; out of every category sets `navSection = "none"`), and `setCategoryImage`. A section's optional `image` (`/media/…` or https, `isCategoryImage`) replaces the automatic icon (`lib/category-icon.ts`, keyword match or a hash of the title, so the same everywhere) in the dashboard and on the home cards; `saveNavigation` keeps it. Order and groups are still edited at `/admin/navigation`.

### Rendering and caching

- Public reads in `lib/data/site.ts` are `"use cache"` with `cacheLife("max")` and tags `pages`, `navigation`, and `settings`. Dashboard server actions call `updateTag(...)`. The scheduler route uses `revalidateTag(tag, { expire: 0 })`, because `updateTag` only works in server actions. Writing to the DB outside the app (for example `db:seed`) leaves the in-memory cache stale until the server restarts. Next keeps revalidations in memory only, so at startup `instrumentation.ts` calls `/api/internal/refresh` (CRON_SECRET), which runs `revalidatePath("/", "layout")` and expires every tag: a restarted server or a CI-built image never serves build-time HTML. Internal routes share `authorizedInternal` (`lib/internal-auth.ts`).
- Error boundaries: `app/(site)/error.tsx`, `app/admin/error.tsx` and `app/global-error.tsx` (`components/route-error.tsx`) reload the page once (per minute, sessionStorage guard) for chunk-load/network errors, otherwise offer "Coba lagi" (`retry()`). Next 16's error props are `{ error, retry }`.
- Code blocks are highlighted server-side with Shiki in `lib/content/highlight.ts`, using dual light/dark themes styled by `.code-block` CSS. The TOC ids come from `headingIds()` in `lib/content/doc.ts`, which the renderer consumes in the same order.
- Routes: `app/(site)/` is the public site (its layout loads settings, navigation, and the search index). `app/admin/(auth)` holds login and first-run setup, `app/admin/(panel)` holds the dashboard shell and pages, and `app/admin/(editor)/pages/[id]` is the full-screen editor. `app/(site)/preview/[id]` is the signed-in draft preview. `app/media/[file]` serves uploads, `app/admin/api/media` handles upload and listing, and `app/api/internal/publish-scheduled` is ticked every minute by `instrumentation.ts` (which also calls `app/api/internal/refresh` once at startup).

The page editor shows "Di halaman ini" for the working copy (`components/admin/editor/editor-outline.tsx`): the ## and ### headings readers will get in the published TOC, recomputed on editor updates (once per frame), the heading past the toolbar (or, at the page bottom, the last one in view) marked, and a click scrolls there and puts the cursor at the heading's end. Beside the page from `xl` (from 1760px when the settings or chat panel is open), otherwise a collapsible block above the content (`InlineEditorOutline`, two headings or more).

### AI Write

- AI Write talks to any OpenAI-compatible chat API, with DeepSeek as the default (`https://api.deepseek.com`, models `deepseek-flash` / `deepseek-v4-pro`). Settings live in `settings` under key `ai`, and the API key is encrypted with AES-256-GCM using `ENCRYPTION_KEY` (`lib/crypto.ts`). `AI_API_KEY` in env overrides the stored key, which is never sent to the client.
- `app/admin/api/ai/route.ts` streams NDJSON events (`text` / `thinking` / `error`) from `lib/ai/client.ts`, with prompts built server-side in `lib/ai/prompts.ts`. DeepSeek thinking mode is enabled by default upstream, so requests send `thinking: { type: "disabled" }` unless the setting is turned on. `reasoning_content` is never shown.
- Editor side (`components/admin/editor/ai-*.tsx`): the result is previewed as plain text, then converted from Markdown to HTML with `marked` (raw HTML escaped) and inserted with `insertContentAt`. The target range is remapped through every transaction while the panel is open.

### AI Chat (agent)

- `lib/ai/agent.ts` runs a tool-calling loop (max 6 model turns) through `streamAgentTurn`. Read tools (`search_pages`, `read_page`, `get_site_structure`) execute on the server. The proposal tools (`propose_new_page`, and `propose_page_edit` when a page is open) never write anything: they emit a proposal whose Markdown/MDX is converted to TipTap JSON by `lib/content/mdx-to-doc.ts` (falling back to plain Markdown if the MDX is invalid).
- Conversations are stored per user in `ai_conversations` (`lib/ai/conversations.ts`, actions in `app/admin/_actions/chat.ts`). `app/admin/api/agent/route.ts` owns persistence: it saves the user message, runs the agent, and stores the reply (text, tool labels, proposals, token usage) even if the stream is cut off, while streaming `AgentEvent` NDJSON. The UI is `components/admin/ai-chat.tsx` (`layout="panel"` beside the editor, showing that page's chats; `layout="page"` at `/admin/ai`, with a history column). It includes a per-chat model picker (`listChatModels`) and rename/delete. Applying an edit saves a revision first. "Buat draf" calls `createDraftFromProposal`, which re-converts the Markdown on the server. Chat Markdown is rendered with raw HTML escaped and unsafe link/image URLs removed.
- Proposals stream live: `streamAgentTurn` yields `tool_progress` (accumulated arguments) and `runAgent` turns `propose_*` calls into throttled `draft` events (`key`, `kind`, `title`/`description`, and only the new part of `content`, read with `partialStringFields` from `lib/ai/partial-json.ts`), ending each with `draft_end` after its `proposal`. Drafts are never stored. The UI shows them as a "Menulis…" card (component tags flattened for the chat renderer) and clears them when the stream ends. Page writing follows the fixed `pageWritingGuide()` in `lib/ai/writing-guide.ts`: an outline first, roughly 900–1.800 words, prerequisites, Steps, titled code, callouts, a FAQ and "Langkah selanjutnya". AI Chat gets it in the system prompt (cache-stable), and AI Write's "write" action gets the plain-Markdown variant with an 8000-token floor. If `finish_reason` is `length` and the last tool call's JSON is cut off, the model is told to resend a shorter proposal.
- Agent quality and limits: `search_pages` ranks every doc page (drafts included) by the query's words in title, description and body (`terms`/`stem` from `lib/ai/ask.ts`) and returns a snippet, so multi-word queries work. Up to `MAX_TURNS` (8) model turns; the last one is sent with `tool_choice: "none"` (tools still listed, so the cached prefix holds) plus a note to answer now, so a chat never ends on a tool call. The prompt asks for source links `[Judul](/docs/slug)` and a duplicate check before proposing a new page.
- Chat UI: the history and the model list load independently (listing models asks the provider and can be slow). Auto-scroll follows the reply only while the reader is at the bottom ("Ke pesan terbaru" otherwise). The input grows with its text; Enter sends (not during IME composition), Esc stops. A stopped reply keeps its text and gets `stopped: true` (set by the route when the request is aborted). "Coba lagi" (last reply) and "Edit" (last user message) call `truncateConversation`, which drops that user message and everything after it (not for messages already folded into the summary). Tool steps collapse to "N langkah pencarian"; proposal content has a rendered "Pratinjau" and a "Markdown" tab; replies have "Salin" (`lib/copy-text.ts`).
- Auto-compaction: when the history to send exceeds `COMPACT_AT_CHARS`, everything but the last `KEEP_RECENT` messages is summarised into `summary` / `compactedCount`. Only the summary (in the system prompt) and the newer messages are sent; the UI still shows the full transcript with a divider. `compactConversation` forces it.
- Token savings: the agent's system prompt holds only fixed instructions plus the summary, and the editor's page context is prepended to the **latest** user message only. That way the prompt prefix (tools, system, older history) is byte-identical between requests and hits DeepSeek/OpenAI prompt caching. `stream_options.include_usage` reports usage, including cache hits (`Usage` in `lib/ai/client.ts`, shown under each reply). AI Write also has an in-memory answer cache (`lib/ai/response-cache.ts`, 1 h, keyed by model, settings, and prompt). `fresh: true` bypasses it ("Coba lagi", description).
- The AI settings model field auto-detects models through `GET {baseUrl}/models` (`fetchAiModels`), with manual entry as a fallback.

### Tanya AI (public search answers)

With AI ready and settings key `ask_ai` on (`AskAiSettings`: `enabled`, `perMinute`, `dailyLimit`; defaults `DEFAULT_ASK_AI`, form under Pengaturan → "Tanya AI di pencarian"), the search dialog shows a "Tanya AI" row first (`getAskAiAvailable()`, cached under `settings`, passed to `SearchProvider` as `ai`; `saveAiSettings` now calls `updateTag("settings")` for it). The answer view `components/ask-ai.tsx` is loaded with `next/dynamic` so `marked` stays out of the page bundle, and renders with `renderChatMarkdown` (raw HTML escaped, safe URLs only, images as links). `POST /api/ask` (`readPublicJson`: same-origin, `perMinute` per IP behind `TRUST_PROXY`, 40/min global; bot UAs refused; daily limit = today's sum in `ask_ai_queries`, so restarts don't reset it) retrieves passages with `lib/ai/ask.ts`: `getAskCorpus()` (cached, tags `pages`+`navigation`) splits every published page listed in the navigation into heading-led Markdown chunks with `#anchor` hrefs, and `retrieve()` scores them by keywords (stopwords, 5-letter stems, IDF, title boost; at most 4 pages / ~9k chars; no embeddings, so it works with DeepSeek). No matching passage means a `miss` without calling the model. The model runs with thinking off, temperature 0.2, 1000 tokens, and answers `TIDAK_ADA_JAWABAN` when the passages don't cover it; the route holds back the start of the stream until it can't be that marker. Answers are cached via `lib/ai/response-cache.ts`. Provider errors are logged, not shown to visitors. Questions and misses appear on `/admin/stats` (`getAskStats`).

### Automation

`lib/automation.ts` runs when a person publishes or schedules a doc page (`publishWorkingCopy` in `lib/pages/service.ts`, used by `publishPage`, `createDraftFromProposal`, and the MCP `publish_page` tool). Switches live in settings key `automation` (`AutomationSettings`, defaults `DEFAULT_AUTOMATION` in `lib/data/site.ts`, form under Pengaturan → Otomatisasi). `prepareForPublish` makes one AI request (`completeChat`, JSON reply, 25 s timeout, silently skipped if AI is off or fails) for a missing description and meta title/description, and on a first publish for the navigation section. It also swaps a placeholder `tanpa-judul…` slug for one from the title (`lib/slug.ts`). `pages.navSection` holds the editor's choice: a section id, `"none"`, or null. With null, AI picks a section or answers `new_section` {tab, title}, which `ensureSection` creates (and the tab, matched by title); without AI it is the first section, or `Dokumentasi › Umum` when the navigation is empty. The first publish appends the page to that section with `addToNavigation`, and the scheduler route does the same when a scheduled page goes live. Re-publishing never touches the navigation. The publish result's `filled` tells the editor what changed (shown as the "Otomatis:" banner). The agent still never publishes. Its `propose_new_page` takes `section` and `publish_at` (the latest user message carries the current WIB time), and the chat offers "Buat & jadwalkan" / "Buat & terbitkan" / "Buat semua & jadwalkan", which run only when clicked. Bulk apply awaits each `updateProposal`, because every call rewrites the stored chat. Generated covers come from `app/cover/[...slug]/route.tsx` (`next/og`, published pages only), rendered per `?shape=` (`card` 16:10, `wide` 2.2:1, default 1200×630 for OG) so `object-cover` never crops their text. Use `generatedCover(slug, shape, color)` for the place the image is shown. The colour (`automation.coverColor`: preset id, `"mixed"`, or `#rrggbb`, palette and contrast logic in `lib/cover-palette.ts`) is read from settings by the route and sits in the URL only to bust browser caches. `getPageCards` and the doc page's OG image fall back to them when `automation.cover` is on.

### MCP

- **Server** (`app/api/mcp/route.ts`, `lib/mcp/server.ts`): stateless Streamable HTTP through `createMcpHandler` from `@modelcontextprotocol/server` v2, serving both 2026-07-28 and 2025-era clients. Auth is a personal bearer token (`api_tokens`, SHA-256 stored, `dk_…`, `lib/mcp/tokens.ts`) with scopes `read`/`write`/`publish` (`lib/mcp/scopes.ts`). The factory builds a fresh `McpServer` per request and registers only the tools the token's scopes allow. Writes go through `lib/pages/service.ts`, the same code the dashboard actions use (revisions with reason `mcp`, automation on publish). The route also checks `isSameOrigin` (DNS rebinding) and a per-token rate limit. Tools run inside the SDK, outside the request scope Next.js tracks, so `revalidateTag` called there is silently lost. Instead, tools collect stale tags, and the route reads a `tools/call` response to the end (2025 clients get SSE) before expiring them. Tokens are managed at `/admin/mcp` (`components/admin/mcp-tokens.tsx`, actions in `app/admin/_actions/mcp.ts`).
- **Client** (`lib/mcp/external.ts`): admins register remote MCP servers (settings key `mcp_servers`, headers AES-GCM encrypted). Saving connects with `@modelcontextprotocol/client` and stores each tool's schema, so chats never list tools at runtime and the agent's tool prefix stays cache-stable. New tools default to enabled only when the server sets `readOnlyHint`. `runAgent` adds enabled tools as `mcp_<server>_<tool>` functions, and `runTool` calls them with a fresh connection (30 s timeout, result truncated to 20k chars). The system prompt tells the model that their output is data, not instructions.
- `lib/pages/service.ts` holds the shared page operations (`saveWorkingCopy`, `publishWorkingCopy`, `unpublish`, `createPageFromMarkdown`) and zod schemas. Callers do the auth and pass `invalidate`: `updateTag` in server actions, collected tags in `/api/mcp`.

### Redirects

`proxy.ts` (matcher `/docs/:path+`) answers old /docs paths with a 308 from the `redirects` table. When `updateSlug` changes the slug of a page that was ever public, `recordSlugChange` (`lib/redirects.ts`) stores the old path pointing at the page **id**, so later renames never create chains, and it drops any redirect from the new path. Manual redirects (`toUrl`: a site path or http(s) URL) are managed by admins at `/admin/redirects` (actions in `app/admin/_actions/redirects.ts`). A published page always wins over a redirect from its own path, and an automatic redirect whose page is off the site falls through to 404. The proxy keeps every live redirect in a `globalThis` map that reloads after 60 s or when `forgetRedirects()` runs (`refreshPublicSite`, publish/unpublish in `lib/pages/service.ts`, the scheduler). `uniqueSlug` treats redirected paths as taken, so generated slugs don't hijack old addresses. Hits are counted with `event.waitUntil`.

### Reader statistics and feedback

Articles (all three layouts, not previews) get `components/reader-footer.tsx` through a `footer` prop: it sends one view per tab (sessionStorage) and shows the 👍/👎 question with an optional private message. Search (`components/search.tsx`) reports normalised queries after 1.5 s idle or on close, with whether they found anything. The public endpoints `app/api/track` and `app/api/feedback` go through `readPublicJson` in `lib/reader.ts` (same-origin, 4 KB cap, per-IP limits only with `TRUST_PROXY`, global caps, zod) and only count published doc pages. Bots, requests without a user agent, and visitors with a `docsku_session` cookie are not counted, and no IP is stored. A message can be attached to a vote once, within 30 minutes. Tables: `page_views` (per page per Asia/Jakarta day), `page_feedback`, and `search_queries`. The dashboard is `/admin/stats` (queries in `lib/data/stats.ts`, actions in `app/admin/_actions/stats.ts`, open to editors): range switch (7/30/90) beside the title, four cards with the change against the previous range, a per-day bar chart (even scale from `niceMax` so the middle line is whole, values on hover/focus), top pages with view bars and a coloured helpful share, "Pencarian" and "Tanya AI" panels (most asked next to no results; a miss links to `/admin/ai?tulis=<query>`, which pre-fills, never sends, a request to write about it via `AiChat`'s `initialInput`), and reader feedback with per-filter counts (`getFeedbackCounts`).

### Comments

Published doc pages have public comments (`page_comments`: one level of replies, status `pending`/`approved`/`spam`, `is_staff`). `ReaderFooter` renders `components/page-comments.tsx`, which fetches `GET /api/comments?slug=` after load, so the article stays prerendered. The response says whether comments are on (settings key `comments`, `CommentSettings`, defaults `{ enabled: true, moderation: false }`, read with the cached `getCommentSettings()`) and whether the reader is signed in (`viewer`). `POST /api/comments` goes through `readPublicJson` (same-origin, 12 KB, 3/min per IP behind `TRUST_PROXY`, 30/min global) plus 10 per page per 10 minutes, a honeypot and a 3 s minimum fill time. Visitor comments are shown at once unless manual moderation is on; any link makes them pending and more than 3 links marks them spam. A signed-in user (session checked on the server, never a client flag) comments under their account name with a "Tim" badge, approved at once. Bodies are plain text (no HTML, links not clickable), and emails are shown only in the dashboard. `/admin/comments` (editors and admins; `lib/comments.ts`, actions in `app/admin/_actions/comments.ts`, UI `components/admin/comments-manager.tsx`) is laid out like WordPress's comment screen: status links with counts (Semua = not spam, Perlu dibalas = the newest message of each conversation whose last word is a visitor's, Menunggu, Disetujui, Spam; `?view=`, old `?status=` still read), a GET form to filter by page (`?halaman=`) and search text/name/email (`?q=`), 20 rows per page (`?p=`, `listCommentRows`, `COMMENTS_PER_PAGE`), bulk actions (`moderateComments`, `deleteComments`), and one compact row per comment (author, text clamped to four lines with "Membalas …", page with its approved-comment count, date). Pending rows have an amber edge. Row actions (Setujui/Sembunyikan | Balas | Spam | Hapus | Lihat) show on hover or focus. "Balas" opens a reply box under the row: Ctrl+Enter sends, Esc closes, quick-answer chips, and "Saran AI" (AI Write `custom` action with the comment and its parent as context; it fills the box, never sends). Replying to a pending comment approves it. A new team comment on any published page is in a collapsible block at the bottom. Public comment sections have `id="komentar"`, which "Lihat" links to. The switches live under Pengaturan → Komentar.

### Author profiles

Each user has a public author profile on `users` (`username` = slug of `/penulis/<username>`, `avatar` = `/media/…` or https, `jobTitle`, `bio`, `links` `{label,url}[]`; rules, `usernameError`, `suggestUsername`, `initials` in `lib/authors.ts`). Profil (`/admin/profile`, `components/admin/profile-forms.tsx`, actions in `app/admin/_actions/profile.ts`) has a header card with the photo (`AvatarEditor`: uploads through `/admin/api/media`, ≤2 MB PNG/JPG/WebP/GIF, then `setAvatar`, which only accepts files in the media library), "Profil publik" (`updatePublicProfile`: name, username with a live `checkUsername` (format, reserved words, taken), job title, bio ≤300, ≤4 https links, and a live preview of the author box), "Akun" (`updateEmail`), "Keamanan" (password + `TwoFactorPanel`, anchor `#2fa`) and the MCP link, with an in-page nav. `components/avatar.tsx` (`Avatar`: photo, or initials on a colour from the name; no hooks) is used in the sidebar, Pengguna, the editor and the public site. A page's author is `coalesce(author_id, updated_by_id)`; the editor's settings panel changes it (`AuthorSection` → `setPageAuthor`, immediate, logs `page.author`). Public reads: `getPublishedPage`/`getInternalPage` return `authorId`; `lib/data/authors.ts` (`getAuthor`, `getAuthorPage`, `getAuthorUsernames`, cached under `authors` (+`pages`); profile, author, user-delete and switch actions `updateTag("authors")`). ### Content review (Tinjauan)

`/admin/review` (`app/admin/(panel)/review/page.tsx`, editors and admins, full width via `WIDE`; data in `lib/review.ts`, actions in `app/admin/_actions/review.ts`) has two tabs. **Jadwal tinjauan**: published doc pages are due when `coalesce(reviewed_at, published_at) + interval < now()`; the interval is `pages.review_interval_days` (null = site default, 0 = never) or settings key `review` (`ReviewSettings` `{ enabled, defaultIntervalDays }`, default `{ true, 180 }`, form under Pengaturan → `#tinjauan`, admin only). `dueAtSql` (alias `p`) reads the settings row inside SQL so any query can use it. Publishing (`publishWorkingCopy`, the scheduler) sets `reviewed_at`; "Tandai ditinjau" (`markReviewed`) does too. Lists: overdue and "Segera" (≤ `SOON_DAYS` = 14), filter `?milik=saya` (owner, or author when unowned). The editor's settings panel has `ReviewSection` (`components/admin/editor/review-section.tsx`), which loads its own data through `getPageReview`: owner (`pages.owner_id`), interval, mark reviewed. **Tautan rusak** (`?tab=tautan`): `scanLinks()` walks the live content of published doc pages (`linksOf`: link marks, `attrs.href`, image `src`, `href`s in array attributes) and reports `/docs` links to missing or unpublished pages (a `redirects` row turns it into "Lewat redirect", not counted as broken), `#anchors` without a heading (`headingIds`, plus `komentar`), missing `/media` files, invalid hrefs, and public pages linking to internal ones. Absolute links to `SITE_URL` are treated as internal. External http(s) links are checked only on demand ("Periksa tautan luar" → `runExternalLinkCheck` → `lib/link-check.ts`): HEAD then GET, 8 s, 4 at a time, ≤200 URLs oldest-first, 90 s budget, one run per server, ≤3 redirects re-checked per hop, results in `link_checks`. 401/403/429 count as "menolak pemeriksa", not broken. SSRF guard: http/https only, no credentials, IP literals and local names refused up front, and every hostname resolved through `guardedLookup` (passed as the request's `lookup`, `agent: false`), which refuses any non-public address (`net.BlockList`; IPv4-mapped and NAT64 `64:ff9b::/96` judged by their IPv4 part), so DNS rebinding can't reach internal hosts. The sidebar item "Tinjauan" shows `NavCounts.review` (overdue count); the dashboard's "Perlu perhatian" lists overdue reviews and `countBrokenLinks()`. The scan runs on every load of those two pages (fine for hundreds of pages; cache it if sites grow large).

### Help widget

Other sites embed the docs with `<script src="https://<docs>/widget.js" async></script>`. Settings live in key `widget` (`WidgetSettings`; defaults and origin helpers in `lib/widget.ts`; cached `getWidgetSettings()`). The form is Pengaturan → "Widget bantuan" (`components/admin/widget-settings-form.tsx`; action `saveWidgetSettings` in `app/admin/_actions/widget.ts`, admins only, which calls `updateTag("settings")`, `forgetWidgetFrame()` and `logActivity`). Allowed origins are https only (http only for localhost), with no path, and `https://*.domain` covers subdomains; at most 20. `app/widget.js/route.ts` is plain JS: a launcher in a shadow root, a lazy iframe of `/widget`, Esc/close/focus return, and full screen below 640px. It reads `data-position`, `data-label`, `data-query` and `data-launcher="false"`, exposes `window.DocskuWidget.open(query)/close()/toggle()`, and any element with `data-docsku-help="words"` opens the widget with that search. It does nothing on origins that aren't allowed, and is a no-op script while the widget is off (`Cache-Control: max-age=300` + ETag). `app/widget/` sits outside `(site)`, so there is no header or footer: `layout.tsx` wraps `WidgetFrame` (`components/widget/frame.tsx`), `page.tsx` is the start screen (`WidgetHome`: the public search index and `search()` from `components/search.tsx`, popular pages, Tanya AI via `components/ask-ai.tsx`), and `a/[...slug]` renders a published public page with `RenderDoc`. The host replies `docsku:init` to the docs origin, and the iframe accepts it only from `window.parent` at an allowed origin, then answers `docsku:ready`. After that it takes only `docsku:open {query}`, and sends `docsku:close` only to that origin. Docs links stay inside the widget (`/widget/a/…`); every other link opens in a new tab. The search query lives in `?q=`, written when the user types; on show, the URL decides, because the router can restore the screen with old state. Framing: `next.config.ts` excludes `/widget…` from the global header rule and gives it `frame-ancestors 'none'` without X-Frame-Options. `proxy.ts` (matcher also covers `/widget` and `/widget/:path*`) replaces it per request with `'self' <origins>` from `lib/widget-frame.ts`, an in-memory copy kept like the redirects map (60 s, dropped on save), or `'none'` when the widget is off or the lookup fails. Searches and views from the widget count in the stats through `/api/track` like the main site's.

### Auth

Sessions live in the DB. The cookie `docsku_session` holds a random token, and the `sessions.id` column stores its SHA-256. Passwords use scrypt (`lib/auth/`). `lib/auth/dal.ts` is the data access layer, and every admin page and server action calls `requireUser` / `requireAdmin` / `authorize` itself, because layouts are not a security boundary. Roles: `admin` can do everything; `editor` can work with pages and media but not navigation, settings, or users.

`proxy.ts` only serves /docs redirects (see Redirects) and the widget's `frame-ancestors` (see Help widget); it is not an auth layer. Every `/admin/api/*` route handler calls `isSameOrigin` (`lib/auth/request.ts`) before anything else; server actions get Next's own origin check. Forwarded headers (`X-Forwarded-For`/`-Host`) are trusted only with `TRUST_PROXY=1` (or `cloudflare`, where `clientIp` prefers `CF-Connecting-IP`; only safe when the origin accepts Cloudflare traffic alone), so failed logins are limited per account (10 per 15 min) and, behind a trusted proxy, also per IP (in-memory, `lib/auth/rate-limit.ts`). Security headers (`frame-ancestors 'none'`, `X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`, HSTS when `x-forwarded-proto: https`) come from `headers()` in `next.config.ts`; `/media/*` gets `default-src 'none'` through a later rule, because a later rule replaces the same header key. The scheduler only calls its own `PORT` (or `SCHEDULER_URL`), never a guessed port.

Two-step login (TOTP, `lib/auth/totp.ts`: RFC 6238 SHA-1/6 digits/30 s, ±1 step, a code can't be reused within its window per process). Users turn it on in Profil → "Verifikasi dua langkah" (`components/admin/two-factor.tsx`, actions in `app/admin/_actions/two-factor.ts`): `startTwoFactor` returns a QR (server-side SVG from `qrcode`) plus an AES-GCM sealed `{user, secret, time}` blob; nothing is stored until `confirmTwoFactor` checks the first code, then `users.totpSecret` (encrypted with `ENCRYPTION_KEY`; changing that key makes secrets unreadable, so those users need a recovery code or an admin reset), `totpEnabledAt` and ten recovery codes (SHA-256 in `users.recoveryCodes`, shown once) are saved. Disabling and new recovery codes need the password or a current code (10 tries/15 min). With 2FA, a correct password creates a `login_challenges` row plus the httpOnly `docsku_mfa` cookie (10 min, path `/admin`; `lib/auth/two-factor.ts`), never a session; `/admin/login/verify` (`verifyLoginAction`) accepts a TOTP or a single-use recovery code (consumed with one `array_remove` update), allows 5 wrong codes per challenge and counts failures toward the per-account/IP login limits, and only then calls `createSession`. `safeNext` allows `/admin…`, `/internal` and `/docs/…` as the post-login target. Admins can "Atur ulang 2FA" in Pengguna. Pengaturan → Keamanan (settings key `security`, `getSecuritySettings()` in `lib/data/security.ts`, cached under `settings`) can require 2FA for admins: an admin without it is sent to `/admin/profile?2fa=wajib` after login and sees a banner in the panel layout; it can only be turned on by an admin who already uses 2FA, and editors are unaffected.

Activity log: `logActivity({ user, action, target, meta })` (`lib/activity.ts`, never throws) is called after successful server actions, the media upload route, MCP write tools (actor = token user, `meta.via = "mcp"`), the scheduler (actor "Sistem"), and auth events (`auth.login`/`logout`/`login_failed` only for existing accounts/`2fa_*`). Actions are dotted verbs grouped by prefix (`ACTIVITY_KINDS`); never log secrets (AI keys, header values, passwords). `/admin/activity` (admins, full width via `WIDE`) renders entries as Indonesian sentences from `lib/activity-text.ts` (add a line there for a new action), grouped by Jakarta day, filtered by `?orang=`, `?jenis=`, `?hari=`, `?halaman=<pageId>` (per-page history), 50 per page; targets link only while they exist. Entries older than 365 days are pruned by `pruneActivity()` from the scheduler tick (at most every 6 h). Reader comments and draft autosaves are deliberately not logged.

### Gotchas

- Never use the browser's `confirm()`/`prompt()`/`alert()` in the dashboard. Use `await confirmDialog({ title, message, confirmLabel, tone: "danger" })` or `await promptDialog({...})` from `components/admin/dialog.tsx` (rendered by `<DialogHost />` in `app/admin/layout.tsx`). Danger dialogs focus "Batal", so a stray Enter never confirms.
- Block drag-and-drop is custom (`components/admin/editor/block-handle.tsx`), because the official TipTap drag handle imports Yjs collaboration packages. A plugin reports the hovered top-level block through a small pub/sub bus, so the editor doesn't re-render on every mouse move. Drops are handled in `handleDrop` (upper half of a block inserts before it, lower half after) with a custom drop line. Keyboard shortcuts are Alt+↑/↓.
- The editor uses `enableContentCheck`. If a stored document contains a node type the editor doesn't know, it locks read-only and never autosaves, because otherwise TipTap would replace the document with an empty one. Register every new node in the `extensions` list of `page-editor.tsx`.
- Server action arguments drop objects with a null prototype, and ProseMirror creates node `attrs` that way. Always send `JSON.parse(JSON.stringify(editor.getJSON()))` (`docJSON` in `page-editor.tsx`).
- React 19 resets forms after an action runs, so server actions return the submitted `values` (see `keepValues` in `lib/validation.ts`) and inputs use them as `defaultValue`.
- Files with `"use server"` may only export async functions. Shared zod schemas and types live in `lib/validation.ts`.
- Dynamic admin pages keep the page component synchronous and put `requireUser()`, `searchParams`, and DB reads in an async child under `<Suspense>`. Without that, the dev overlay reports an "uncached data outside Suspense" error. `app/admin/layout.tsx` sets `instant = false`.
- Use SQL `now()` instead of `new Date()` in queries that run while rendering. Cache Components rejects `new Date()` during prerender.
- Next 16 blocks dev assets for non-localhost origins. `next.config.ts` adds the machine's IPs and `DEV_ORIGINS` to `allowedDevOrigins`.

Per `AGENTS.md`, the bundled docs in `node_modules/next/dist/docs/` (`01-app/` for the App Router) are the source of truth for Next.js APIs. Read them instead of relying on prior knowledge.

`next.config.ts` turns on several non-default behaviors that affect how code must be written:

- **`cacheComponents: true`**: Data is uncached by default. Cache async functions and components explicitly with the `"use cache"` directive (plus `cacheLife`/`cacheTag` from `next/cache`). Uncached async work (DB queries, `cookies()`, `headers()`, `params`, `searchParams`) must sit inside a `<Suspense>` boundary. `dynamicParams` is not allowed, so call `notFound()` instead, and `generateStaticParams` must return at least one param. See `01-getting-started/08-caching.md` and `02-guides/migrating-to-cache-components.md`.
- **`partialPrefetching: true`**: `<Link>` prefetches only the route's static/cached "App Shell". URL-dependent data goes behind Suspense, and sidebar links use `<Link prefetch={true}>`. See `02-guides/adopting-partial-prefetching.md`.
- **`reactCompiler: true`**: The React Compiler auto-memoizes components, so manual `useMemo`/`useCallback`/`memo` are usually unnecessary.
- **Tailwind CSS v4 via Turbopack**: Tailwind is wired through a `turbopack.rules` loader (`@tailwindcss/turbopack`) for `*.css` instead of PostCSS, and there is no `postcss.config` or `tailwind.config`. Theme tokens are CSS variables in `app/globals.css` (`:root` / `.dark`) exposed through `@theme inline` (`bg-page`, `text-fg-muted`, `border-line`, `text-accent`, …).

Route props use Next's globally generated helper types (`PageProps<"/docs/[...slug]">`, `LayoutProps<"/">`, `RouteContext<"/media/[file]">`), generated into `.next/types`.
